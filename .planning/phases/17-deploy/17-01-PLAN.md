<objective>
Fechar a pré-condição de infraestrutura da Fase 17 antes de tocar em qualquer coisa que suba imagem:
medir a RAM real da VPS compartilhada (que agora hospeda EasyPanel + WordPress + MySQL em produção,
além do que este projeto vai adicionar) e parametrizar o código para que o domínio de produção — que
ainda nem resolve em DNS — não precise estar hardcoded em nenhum arquivo.

A arquitetura mudou no meio do planejamento desta fase: a decisão travada original era GHCR + Caddy
(`docs/adr/004-deploy-ghcr-caddy.md`), mas a VPS já roda EasyPanel com um site WordPress real no ar em
`allmusicbr.com`. Um Caddy nosso fazendo bind em 80/443 derrubaria esse site. A infraestrutura de
produção passa a ser: **build no GitHub Actions, push para GHCR (mantido) + EasyPanel como dono do
proxy reverso, dos domínios e do TLS (troca o Caddy)**. Esse plano registra essa divergência como ADR
e prepara o código para o novo desenho, sem ainda subir nada.

Purpose: sem o número real de RAM, subir Next + Strapi + Postgres ao lado do WordPress é apostar que
o host aguenta — e se não aguentar, o processo morto pode ser o do cliente, não o nosso. Sem o
remotePatterns dinâmico, as imagens do catálogo (rota já entregue na Fase 5) não carregam em produção
ou o otimizador de imagem precisaria ser desligado, o que reabriria a proteção contra SSRF que o
projeto decidiu manter ligada desde a Fase 1.

Output: Dockerfile e next.config.ts prontos para receber o hostname do CMS via build-arg; ADR da
mudança de arquitetura; esqueleto de `docs/DEPLOY.md` com o orçamento de RAM medido; `robots.ts`
bloqueando indexação da beta.

   `sharp`, 256–384 MB para o Postgres), com folga adicional para picos de build/admin do Strapi.
   Se a RAM disponível reportada em (c) for **menor que 2 GB**, **pare aqui** e devolva a decisão ao
   invés de prosseguir: as opções documentadas em `docs/DEPLOY.md` (criado na Task 3) são
   (i) fazer upgrade do plano de RAM da VPS na Hostinger, (ii) criar um swapfile temporário via SSH
   como mitigação (não solução) enquanto o upgrade não sai, ou (iii) revisar o footprint do
   WordPress/EasyPanel existente. Só avance para as próximas tarefas — e para os planos 17-02/17-03 —

  <action>
Em `next.config.ts`, tornar o array `images.remotePatterns` parcialmente dinâmico: manter as duas
entradas fixas de desenvolvimento (`localhost:1337` e `cms:1337`, ambas `http`, `pathname: '/uploads/**'`)
e, além delas, ler `process.env.NEXT_PUBLIC_STRAPI_MEDIA_URL`; se a variável existir e for uma URL
válida (`new URL(...)`, dentro de um `try/catch` — build local sem essa variável não pode quebrar),
acrescentar mais uma entrada ao array usando o `protocol` (sem os dois-pontos), `hostname` e `port`
extraídos dessa URL, com o mesmo `pathname: '/uploads/**'`. Comentar no arquivo, ao lado dessa
entrada, por que ela existe: em produção o CMS roda atrás do próprio domínio público (decisão da
Fase 17 — ADR 005), e o otimizador de imagem do Next precisa da allowlist exata desse host porque a
flag `unoptimized` **nunca** é desligada como atalho (nunca remover essa allowlist para "resolver"
um erro de imagem — reabre a proteção contra SSRF que o comentário logo acima já explica). Não
transformar isso num objeto `Record` genérico nem aceitar `*` como hostname — a entrada é sempre um
host único, resolvido de uma variável de ambiente específica.

No `Dockerfile`, no estágio `builder` (antes da linha `RUN npm run build`), acrescentar
`ARG NEXT_PUBLIC_SITE_URL` e `ARG NEXT_PUBLIC_STRAPI_MEDIA_URL`, seguidos de
`ENV NEXT_PUBLIC_SITE_URL=$NEXT_PUBLIC_SITE_URL` e `ENV NEXT_PUBLIC_STRAPI_MEDIA_URL=$NEXT_PUBLIC_STRAPI_MEDIA_URL`
— isso é o que faz o valor passado por `--build-arg` no GitHub Actions (plano 17-02) chegar a
`process.env` durante o `npm run build` deste estágio. Comentar a razão (variável `NEXT_PUBLIC_`
congela no build, não é lida em runtime pelo `server.js` standalone) para que ninguém tente "corrigir"
isso movendo para o estágio `runner` depois. Não adicionar valor-padrão nos `ARG` (sem default — se
faltar no build, o `next.config.ts` já trata a ausência sem quebrar, per o `try/catch` acima).

Não mexer em mais nada do Dockerfile (o restante — `deps`, `runner`, `USER nextjs` — já está correto
e não muda com esta fase).

## Trust Boundaries

| Build-arg do Docker → bundle do Next | Valor de `NEXT_PUBLIC_*` congela no build; não é segredo, mas precisa ser o valor certo |

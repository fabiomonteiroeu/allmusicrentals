<objective>
Colocar o site no ar: workflow do GitHub Actions que builda, publica no GHCR e dispara o redeploy dos
dois servicos no EasyPanel, e a criacao guiada dos tres servicos (Postgres, cms, web) no painel -- o
agente nao tem acesso ao painel nem a VPS, entao esta tarefa e majoritariamente checkpoint. Termina
com `https://rentals.allmusicbr.com` e `/catalogo` respondendo por HTTPS de verdade.

Decisao de arquitetura desta etapa (detalhada no ADR 005, criado no plano 17-01): como o EasyPanel ja
e o dono das portas 80/443 nesta VPS, cada servico nosso ganha um dominio proprio gerenciado por ele --
`web` em `rentals.allmusicbr.com` e `cms` em `cms.rentals.allmusicbr.com`. Expor o Strapi por HTTPS
(em vez de mante-lo so interno) resolve tres problemas de uma vez: (1) o valor de
`NEXT_PUBLIC_STRAPI_MEDIA_URL` fica congelado no build da imagem do Next (ver 17-01, Task 2) -- precisa
ser um endereco estavel, e um dominio publico controlado por nos e mais confiavel do que adivinhar o
nome de rede interna que o EasyPanel atribui a cada servico (nao documentado publicamente); (2) o
webhook de revalidacao do Strapi recusa alvo nao-publico em `NODE_ENV=production` (risco ja registrado
em `.planning/STATE.md`) -- apontar para `https://rentals.allmusicbr.com/api/revalidate` resolve isso
sem configuracao especial; (3) o proprio acesso ao admin do Strapi para cadastrar conteudo, gerar
token e configurar o webhook precisa de alguma porta de entrada -- a alternativa (tunel SSH
permanente) e mais fragil para uso recorrente da equipe de conteudo. O Strapi mantem sua propria
autenticacao de admin; a Postgres nunca ganha dominio (fica so na rede privada do EasyPanel).

Purpose: sem isto, nao existe pipeline de publicacao nem site no ar -- e o coracao da Fase 17 sob
prazo de 24h.
Output: `deploy.yml` publicando em GHCR e disparando o redeploy; os tres servicos criados no
EasyPanel; `rentals.allmusicbr.com` e `cms.rentals.allmusicbr.com` respondendo por HTTPS valido.
</objective>

`group` baseado em `github.ref` e `cancel-in-progress: false` (nunca cancelar um deploy em andamento
no meio). Bloco `permissions` com `contents: read` e `packages: write` -- e o que permite
`docker/login-action` usar o `GITHUB_TOKEN` automatico para publicar no GHCR, sem secret adicional
para o push.

Um job unico. Primeira metade repete os checks do `ci.yml` (checkout, setup-node 22 com cache npm,
`npm ci`, `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm test -- --ci`,
`npm run build`), e imediatamente depois roda `node scripts/verifica-segredo-no-bundle.mjs` -- este e
o item do risco de `.planning/STATE.md` que diz que essa varredura "nao esta no CI"; aqui ela entra
no caminho critico do deploy, entao nenhuma imagem e publicada sem passar por ela.

Segunda metade: `docker/setup-buildx-action@v3`, depois `docker/login-action@v3` com
`registry: ghcr.io`, `username` vindo de `github.actor`, `password` vindo do `GITHUB_TOKEN` do
workflow. Dois passos de `docker/build-push-action@v6`:
- imagem `web`: `context: .`, `push: true`, duas tags -- `ghcr.io/<github.repository>/web:latest` e
  `ghcr.io/<github.repository>/web:<github.sha>` (o repositorio ja e `fabiomonteiroeu/allmusicrentals`,
  em minusculas, sem necessidade de normalizacao manual) -- e `build-args` com duas entradas:
  `NEXT_PUBLIC_SITE_URL` valendo `https://` concatenado com o secret `DOMINIO`, e
  `NEXT_PUBLIC_STRAPI_MEDIA_URL` valendo `https://cms.` concatenado com o mesmo secret `DOMINIO`. E
  este passo que faz o dominio chegar ao `ARG` criado em 17-01 -- nunca escrever o dominio literal
  aqui, sempre via `secrets.DOMINIO`.
- imagem `cms`: `context: ./cms`, `push: true`, as mesmas duas tags trocando `web` por `cms`. Sem
  `build-args` -- o Strapi nao precisa de nada no build, so em runtime.

Por fim, dois passos de `run` chamando `curl -fsS -X POST` para a URL de cada um dos dois secrets
`EASYPANEL_DEPLOY_HOOK_WEB` e `EASYPANEL_DEPLOY_HOOK_CMS`, nesta ordem, sem `if` (uma falha no
primeiro deve interromper o job antes do segundo -- deploy parcial e pior que nao fazer). Comentar no
arquivo que o metodo exato (POST ou GET) e o formato da URL devem ser confirmados contra o que o
painel do EasyPanel mostrar na aba Deployments (a Task 2 deste plano e quem descobre isso na pratica);
se a chamada com POST devolver 404 ou 405, o ajuste e trocar para uma chamada GET simples.

Nao reintroduzir SSH nem comando de `docker compose` -- o redeploy e inteiramente via webhook do
EasyPanel, que ja faz o pull da tag mais recente e recria o container.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions -> GHCR | O `GITHUB_TOKEN` publica imagem no registry do próprio repositório |
| GitHub Actions -> EasyPanel (webhook) | Uma URL com token secreto dispara redeploy — quem tiver a URL pode redeployar |
| Internet -> `cms.rentals.allmusicbr.com` | Painel admin do Strapi e API pública ficam expostos por HTTPS |
| EasyPanel -> GHCR | PAT de leitura fica armazenado dentro do painel para puxar imagem privada |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-17-04 | Spoofing | URL de redeploy do EasyPanel | mitigate | A URL contém um token secreto próprio do EasyPanel, vive só em GitHub Secrets, nunca em log do workflow (`curl` sem `-v`) |
| T-17-05 | Information Disclosure | PAT do GitHub para pull do GHCR | mitigate | Escopo restrito a `read:packages`; nunca vira GitHub Secret nem entra no repositório — fica só dentro do EasyPanel |
| T-17-06 | Elevation of Privilege | Admin do Strapi exposto publicamente em `cms.rentals.allmusicbr.com` | accept | Autenticação própria do Strapi; senha forte exigida no bootstrap (plano 17-03); allowlist de IP fica deferida — ver seção de escopo não coberto do plano 17-03 |
| T-17-07 | Tampering | Permissões do `GITHUB_TOKEN` no workflow | mitigate | `permissions: contents: read, packages: write` explícito — nunca o padrão amplo |
| T-17-SC | Tampering | GitHub Actions de terceiros (`docker/login-action`, `docker/build-push-action`, `docker/setup-buildx-action`) | mitigate | Ações oficiais do namespace `docker/`, fixadas por tag de versão major; nenhum pacote npm/pip/cargo novo neste plano |
</threat_model>
